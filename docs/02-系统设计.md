# 秒杀系统设计说明

> 这份文档记录"为什么这么设计"，是报告 2.1（项目概述 + 顶层结构 + 数据库设计）和
> 2.2（主要功能与性能 + 技术路线 + 详细设计）的底稿。代码在 `seckill-order-queue/`。

## 一、题目拆解

选题 #15 的原话是「电商"秒杀"系统的订单处理队列优化」。这句话里有三个词值得拆：

- **秒杀**：库存极少、瞬时请求极多、同一件商品被几十万人同时抢。它不是"访问量大"，
  而是"**写冲突集中在一个点上**"——所有请求都要去改同一行库存。
- **订单处理队列**：请求不能都在请求线程里同步做完。下行要有一个缓冲，
  把"扣减成功"和"生成订单、落库"解耦，否则数据库会被打死。
- **优化**：题目要的是对比，不是"写出一个能跑的秒杀"。所以必须能**换掉队列、换掉锁、
  换掉线程池参数**，跑同一份压力，量出差别。

由此确定三条设计红线：

1. **库存扣减必须绝对不超卖**。这是秒杀系统的正确性底线，比性能优先。
2. **队列、锁、线程池、限流、去重必须是可替换的组件**，否则没法做对比实验。
3. **必须能观测**。没有指标就只能凭感觉说"快了"，所以要有一块面板实时看库存、
   成交数、吞吐、分位延迟、队列深度。

```
┌──────────────────────────────────────────────────────────┐
│  浏览器监控面板（原生 HTML/CSS/JS + Chart.js）              │
│  2s 轮询 /api/metrics，3s 轮询 /api/orders                 │
└───────────────────────┬──────────────────────────────────┘
                        │ HTTP / JSON
┌───────────────────────▼──────────────────────────────────┐
│  server 层                                                │

└───────────────────────┬──────────────────────────────────┘
                        │ 同进程直调
┌───────────────────────▼──────────────────────────────────┐
│  order/SeckillEngine —— 核心链路                          │
│                                                           │

│  ② 去重 Deduplicator ─┤  三者在请求线程上同步执行          │

│  ④ 生成订单 + 入队 TaskQueue                              │
│  ⑤ 消费线程组 OrderWorker → 落库 OrderStore               │
│  ⑥ 定时扫超时未支付 → 回补库存                            │
└───────┬───────────────────────────┬──────────────────────┘
        │                           │
   ┌────▼─────┐              ┌──────▼──────┐
   │ stock/   │              │ persistence/│

   └──────────┘              └─────────────┘
   ┌──────────┐  ┌───────────┐  ┌──────────┐
   │ queue/   │  │ dedup/    │  │ ratelimit/│
   │ 4 种队列 │  │ 3 种去重  │  │ 3 种限流 │
   └──────────┘  └───────────┘  └──────────┘
              ┌────────────────────┐
              │ metrics/ 指标与直方图│
              └────────────────────┘
```

分层的理由：**每一个可替换的东西都藏在一个接口后面**。`Stock`、`TaskQueue`、
`Deduplicator`、`RateLimiter`、`OrderStore` 全是接口，实验时用不同的实现拼出不同的引擎，
业务代码一行不用改。这是能把 7 组对比实验跑起来的前提。

## 三、核心链路（一次抢购请求的完整生命周期）

```java
// SeckillEngine.seckill() —— 跑在请求线程上，必须极短
long t0 = System.nanoTime();
metrics.recordRequest();
try {
    return doSeckill(req, t0);
} finally {
    metrics.recordRequestLatency(System.nanoTime() - t0);   // 全部请求都记
}
```

`doSeckill` 内部的顺序是固定的，顺序本身有讲究：

| 步 | 动作 | 为什么在这个位置 |
|---|---|---|
| 1 | 限流 `limiter.tryAcquire()` | 最便宜的一道闸，先挡掉超量流量，省下后面所有开销 |
| 2 | 去重 `dedup.firstSeen()` | 挡掉重复点击。放在扣库存之前，避免重复请求把库存扣走 |
| 3 | 扣库存 `stock.tryDeduct()` | 唯一真正需要原子性的操作，也是唯一的争用点 |
| 4 | 生成订单号并入队 | 扣成功才建单。入队失败必须 **`stock.restore()` 回补** |
| 5 | 消费线程落库 | 异步，与请求线程解耦 |
| 6 | 定时扫超时 | 30 秒未支付的订单关闭并回补库存 |

第 4 步的补偿是最容易漏的地方：库存已经扣了，队列却满了（`offer` 返回 false），
如果这时直接返回"系统繁忙"而不回补，这件商品就**凭空消失**了。代码里是这样写的：

```java
if (!queue.offer(task)) {
    stock.restore();          // 关键：扣了没入队，必须还回去
    metrics.recordRejected();
    return SeckillResult.fail(SeckillResult.Status.REJECTED);
}
```

第 5 步落库失败同理：进死信并回补，不能静默丢弃。

## 四、库存扣减的五种实现

这是 E2 的被试对象，也是整个项目理论含量最高的地方。

| 实现 | 机制 | 特点 |
|---|---|---|
| `SyncStock` | `synchronized` 方法 | JDK 最老的方案。偏向锁/轻量级锁在争用激烈时膨胀成重量级锁，线程挂起/唤醒 |
| `LockStock` | `ReentrantLock` | 显式锁，可中断、可超时、可公平，但仍是互斥 |
| `StampedStock` | `StampedLock` 乐观读 | 先 `tryOptimisticRead()` 读个快照，只有真的要扣减才升级成写锁。读多写少时几乎无锁 |
| `CasStock` | `AtomicInteger` + CAS 自旋 | 无锁。失败就重读重试，没有线程挂起开销，但高争用下自旋浪费 CPU |
| `AdderStock` | `LongAdder`（安全版） | 分段累加，写性能极好；但**做条件扣减必须额外加锁**，否则 sum 与 increment 之间有窗口 |
| `AdderStock(unsafe)` | `LongAdder` 直接用 | **故意写错的版本**，用来证明"只换原子计数器不够"。E2 的负面对照 |

`AdderStock` 的 unsafe 版本是刻意留的 bug 样本，代码里长这样：

```java
// 错的：先看有没有货，再加。两步之间别人可能已经把货扣光了
if (sold.sum() < capacity) {
    sold.increment();     // 竞态窗口就在这两行之间
    return true;
}
```

`StampedStock` 的乐观读值得单独说，因为它是唯一"读不加锁"的方案：

```java
long stamp = lock.tryOptimisticRead();
int cur = remaining;                       // 裸读，可能是脏的
if (!lock.validate(stamp)) {               // 期间有写发生 → 快照作废
    stamp = lock.readLock();               // 降级成悲观读
    try { cur = remaining; } finally { lock.unlockRead(stamp); }
}
// 只有确定要扣减时才升级写锁
```

## 五、队列的四种实现

| 实现 | 结构 | 关键性质 |
|---|---|---|
| `ArrayBlockingQueue` | 数组 + 一把 `ReentrantLock` | 有界、内存紧凑；生产消费共用一把锁，高并发下重试多 |
| `LinkedBlockingQueue` | 链表 + 两把锁（put/take 分离） | 生产消费不互斥；每个节点一次对象分配 |
| `LinkedTransferQueue` | 链表 + 无锁 `CAS` | 无界，`offer` 永不失手；但 `size()` 要遍历整条链表 |
| `MpscRingQueue`（自写） | 数组 + 每槽序号 + `CAS` 抢尾 | 无锁、零分配；**只能单生产者** |

自写的 `MpscRingQueue` 的设计要点：

- 容量取 2 的幂，取模用 `pos & mask`，省一次除法。
- 每个槽位配一个序号。生产者写完数据把序号推到 `pos+1` 发布；消费者靠序号判断可读。
- 多消费者用 `VarHandle` 的 `CAS` 抢 `tail`，抢输的重读再试。
- `head` 只有生产者写，**不需要原子操作**——这也正是它不能多生产者的原因。
- 前后填 `p0..p6` / `c0..c6` 撑满缓存行，防伪共享。

## 六、数据库设计

底层用 H2（嵌入式，免安装，适合课程作业；接口抽象后用 MySQL 只需换实现）。

```sql
CREATE TABLE orders (
    order_id   BIGINT      PRIMARY KEY,
    user_id    BIGINT      NOT NULL,
    sku_id     BIGINT      NOT NULL,
    request_id VARCHAR(64) NOT NULL,
    status     VARCHAR(16) NOT NULL,   -- CREATED / PAID / CLOSED / DEAD
    created_ms BIGINT      NOT NULL,
    paid_ms    BIGINT      NOT NULL DEFAULT 0
);
CREATE INDEX idx_user    ON orders(user_id);
CREATE INDEX idx_status  ON orders(status);
CREATE INDEX idx_created ON orders(created_ms);
```

三个索引各有用途：`idx_user` 给"我的订单"用，`idx_status` 给对账统计用，
`idx_created` 给超时扫描用（`WHERE status='CREATED' AND created_ms < ?`）。

订单状态机：

```
       扣库存成功、入队
              │
        ┌─────▼─────┐
        │  CREATED  │──── 支付 ────► PAID
        └─────┬─────┘
              │ 超时未支付（30s）
        ┌─────▼─────┐
        │  CLOSED   │  ← 回补库存
        └───────────┘

       落库失败
        ┌───────────┐
        │   DEAD    │  ← 进死信 + 回补库存
        └───────────┘
```

**对账恒等式**（E6 用它判定一致性）：

```
剩余库存 + 已售 + 已关闭 + 死信 = 初始库存
```

任一轮实验结束后这个式子不成立，就说明有订单凭空出现或消失，整轮数据作废。

## 七、可观测性

面板和实验都靠 `Metrics` 这一个类。几个设计决定值得记下：

1. **计数用 `LongAdder` 不用 `AtomicLong`**。15 个线程每秒几十万次自增，
   `LongAdder` 的分段累加比 CAS 自旋快得多，而计数不需要精确的即时一致性。
2. **延迟用固定分桶直方图，不用 `synchronized` 的样本列表**。分位数只需要
   "落进哪个桶"，21 档对数分桶，`record()` 是一次数组自增。
3. **两种延迟要分开记**：
   - `requestLatency`：所有请求的响应时间（含被拒的）。这是用户实际感受。
   - `e2e`：只有成交单的端到端耗时（含排队 + 落库）。这是系统真实处理能力。

   一开始只记了后者，结果 100 倍流量下 P50 反而下降——当时还以为是"优化生效了"，
   真实原因是 99.5% 的请求在扣库存那步就被拒了，根本没进入统计。
   这个坑写进了报告 3.2。

## 八、踩过的坑（对应报告 3.2 的"出错原因分析"）

1. **`LatencyHistogram` 起初不是线程安全的**。`counts[idx]++` 在 200 线程下丢样本，
   面板出现过 p50=0.007ms 这种不可能的值。改成 `LongAdder[]`。
2. **分桶过粗导致分位数退化**。原本每倍频 1 个桶，8.19~16.38ms 是一个桶，
   插值后所有流量档的 p50 都恰好等于桶中点 12.2880ms。改成每倍频 3 个桶。
3. **实验工厂复用了有状态对象**。`runMatrix` 内部工厂要调 8 次（3 预热 + 5 实测），
   库存/令牌桶/去重表若在循环外 `new`，第二轮开始时已耗尽 → 26 组成功数全 0。
   改成在工厂 lambda 内 `new`。
4. **逐字段取中位数导致计数自相矛盾**。E4 出现过 success 1000 + 限流 198901
   + 售罄 344 = 200245 > 总请求数 200000，因为三个数来自不同轮次。
   改成整轮取中位数（按 tps 排序取中间那一整轮）。
5. **深度采样本身成了被测对象**。`queue.size()` 每入队调用一次，
   `LinkedTransferQueue.size()` 要遍历两百万节点，把 LTQ 的引擎内吞吐从 4.19M
   压到 0.35M。加开关关掉后重测，差异立刻反转。
6. **CSV 重复写表头**。`append=false` 被当作"允许写表头"，同一个文件被多个实例
   打开就重复写。加 `firstWrite` 标记。
7. **`tps` 在库存远小于请求量时无意义**。20 万请求 19.9 万在扣库存就被秒拒，
   耗时 63ms，算出 tps=313 万这种荒谬值。拆成三个数：`tps`（总请求吞吐）、
   `order_tps`（有效成交吞吐）、`soldout_ms`（售罄耗时）。
