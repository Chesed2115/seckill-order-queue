# 秒杀系统实验矩阵设计（v1，待确认）

> 用途：这是整个项目的骨架。后面的代码按它实现，报告 2.2/2.3/3.1 的数据全部出自它。
> 请重点看 **第三节的实验分组** 和 **第六节的时间预算**，这两处最影响工作量。

---

## 一、为什么这样分层

题目要求"比较不同队列和锁策略下的吞吐量与延迟"。如果所有实验都走 HTTP 打进去，那么测到的其实是
「Jetty 线程池 + TCP 栈 + JSON 反序列化 + 业务逻辑」的混合值，队列和锁的差异会被网络噪声淹掉，
很可能出现 A 队列比 B 队列快 3% 这种无法解释的结论。

所以实验分成两层：

| 层 | 入口 | 测什么 | 用来回答 |
|---|---|---|---|
| **L1 微基准**（in-process） | 直接调 `SeckillEngine` API | 纯并发结构差异 | 队列/锁/线程池的对比（实验主体） |
| **L2 端到端** | HTTP `/api/seckill` | 含协议栈的真实系统 | 不超卖/不重复的功能验证 + 面板演示 |

L1 是给评分表里"理论知识应用水平（10 分）"和"设计内容（10 分）"撑场面的，
L2 是给"达到预期目标的程度（15 分）"和现场演示用的。

---

## 二、统一控制变量

所有 L1 实验除了被研究的那个自变量，其余全部固定：

```
商品库存        inventory = 1000
总请求数        requests  = 200_000      （即 200 倍超卖比，接近真实秒杀）
虚拟用户线程数   vusers    = 256          （16 物理核 → 16 倍超订，制造竞争）
每个用户请求数   perUser   = 782          （200000 / 256 向上取整对齐）
JVM            JDK 21, -Xms2g -Xmx2g -XX:+UseG1GC
预热            3 轮（不计入结果）
正式            5 轮，取中位数（同时记录 min/max 用于画误差棒）
机器            i7-14650HX 16C24T / 32GB / Windows 11
落库            L1 实验默认关闭持久化（单独由 E6 研究）
```

**为什么是 200 倍超卖**：库存 1000、请求 20 万，扣减成功的只有 0.5%，其余 99.5% 走的是
「读库存 → 发现为 0 → 快速失败」的路径。这条路径的锁竞争形态和"成功路径"完全不同，
是秒杀系统真正的性能瓶颈所在，必须覆盖。

**为什么要 256 个虚拟用户**：本机 16 核 24 线程。vusers 太少（如 16）根本压不出竞争，
太多（如 2000）则大量时间花在 OS 调度上。256 ≈ 10 倍超订，是能找到饱和点又能区分策略的区间。
E3 会单独扫描 vusers 从 8 到 1024 找拐点。

## 三、实验分组

### E1 · 并发队列对比（题目点名的核心）

**自变量**：队列实现

| 编号 | 队列 | 底层结构 | 预期特征 |
|---|---|---|---|
| Q1 | `ArrayBlockingQueue` | 数组 + 单把 `ReentrantLock` | 有界、内存紧凑，但生产消费共用一把锁 |
| Q2 | `LinkedBlockingQueue` | 链表 + 两把锁（putLock/takeLock） | 读写分离锁，吞吐高于 Q1，但有节点分配开销 |
| Q3 | `LinkedTransferQueue` | 链表 + CAS | 无锁，`transfer()` 可直接交接给消费者，延迟低 |
| Q4 | `MpscRingQueue`（自写） | 数组 + CAS + 缓存行填充 | 单生产者多消费者无锁环形队列，零分配 |

> Q4 是自研的。用 `@Contended` 填充 head/tail 消除伪共享，序号用 `long` 而非 `AtomicLong` 对象，
> 这是整个项目里技术含量最高的一块，也是答辩时最能讲的部分。

**同时扫描消费者数**：`workers ∈ {4, 16, 32}`（对应 0.25× / 1× / 2× 物理核）

**矩阵规模**：4 队列 × 3 消费者数 = **12 组配置**，每组 8 轮（3 预热 + 5 正式）= 96 次运行

**产出图**：双 Y 轴柱状图（TPS 柱 + p99 折线），X 轴为配置，按队列分组

---

### E2 · 库存扣减策略对比（题目点名的核心）

**自变量**：扣减实现

| 编号 | 策略 | 并发原语 | 说明 |
|---|---|---|---|
| L1 | `SynchronizedStock` | `synchronized` 方法 | 最朴素，JVM 内置锁 |
| L2 | `ReentrantLockStock` | `ReentrantLock` | 显式锁，支持 `tryLock` 超时 |
| L3 | `StampedLockStock` | `StampedLock` 乐观读 | 读不加锁，扣减时升级为写锁 |
| L4 | `CasStock` | `AtomicInteger` + CAS | 无锁，失败自旋重试 |
| L5 | `LongAdderStock` | `LongAdder` 分片计数 | 只适合"只加不减"场景，此处是**反例对照组** |

> L5 是故意放进去的反例：`LongAdder` 在高并发累加下远快于 `AtomicInteger`，但它**无法做条件扣减**
> （"库存 > 0 才减 1"是一个需要原子性的复合操作，`LongAdder` 做不到）。实测会发现它要么超卖、
> 要么必须外层再加锁从而比 L2 还慢。这个"负结果"写进报告 3.2（出错原因分析）非常有说服力。

**同时扫描竞争强度**：`vusers ∈ {1, 16, 64, 256, 1024}` —— 看各策略的性能曲线在哪里交叉

**矩阵规模**：5 策略 × 5 竞争强度 = **25 组配置**，× 8 轮 = 200 次运行

> 这一组运行次数最多但单次最快（无队列、无落库），实际耗时可接受。

**产出图**：折线图（X=并发线程数对数轴，Y=TPS），5 条线；另附一张"超卖数量"表证明正确性

### E3 · 线程池参数寻优

**自变量**：
- 核心线程数 `corePoolSize ∈ {4, 8, 16, 24, 32, 48}`
- 有界队列容量 `queueCapacity ∈ {256, 1024, 4096, 16384}`
- 拒绝策略 `RejectedExecutionHandler ∈ {AbortPolicy, CallerRunsPolicy, DiscardOldestPolicy, 自定义背压}`

**矩阵规模**：6 × 4 = 24 组（拒绝策略单独在 E7 测）

**产出图**：热力图（X=队列容量，Y=核心线程数，颜色=TPS）

---

### E4 · 限流策略对比

| 编号 | 策略 | 实现 | 特点 |
|---|---|---|---|
| R1 | 无限制 | 直通 | 基线，用于衬托 |
| R2 | 令牌桶 | `Semaphore` + 定时补充 | 允许突发 |
| R3 | 漏桶（平滑） | `ArrayBlockingQueue` 当桶 | 输出恒定，削峰 |
| R4 | 滑动窗口 | `LongAdder` 按秒分桶 | 精确控制窗口内总量 |
| R5 | 自适应 | 根据队列堆积深度动态调速率 | 背压策略，拓展部分 |

**扫描**：`目标 QPS ∈ {10000, 50000, 100000}`

**矩阵规模**：5 × 3 = 15 组

**关键指标**：实际通过率 vs 目标 QPS 的偏差（限流精度）、对被限流请求的响应延迟

---

### E5 · 幂等去重开销

**自变量**：去重实现

| 编号 | 实现 | 内存 | 误判 |
|---|---|---|---|
| D0 | 不去重（会重复下单） | 0 | - |
| D1 | `ConcurrentHashMap<Long,Boolean>` | O(n) | 无 |
| D2 | `CuckooFilter` 风格位图 | 固定 | 有假阳性 |
| D3 | 布隆过滤器 | 固定 | 有假阳性 |

**矩阵规模**：4 组 × 3 种请求重复率（0% / 30% / 90%）= 12 组

**关键指标**：额外延迟、内存占用、假阳性导致的"误杀"订单数

---

### E6 · 超时回补与异常恢复

**不是性能实验，是正确性实验**。构造以下场景，逐一验证：

| 场景 | 构造方法 | 期望 |
|---|---|---|
| 下单后未支付超时 | 订单置为 PENDING，等待 TTL 到期 | 库存自动 +1，订单状态置为 CLOSED |
| 消费者线程抛异常 | 注入 `RuntimeException` | 订单进死信队列，库存不丢（由补偿任务回补） |
| 进程被强杀 | 运行中 `kill -9`，重启 | 从 H2 恢复，对账结果：已售 + 剩余 = 初始库存 |
| 数据库写入失败 | 注入 SQLException | 重试 3 次后进死信，不阻塞队列 |

**判断标准**：`sellable + reserved + sold + dead = inventory_initial` 恒等式成立（这个恒等式会写进报告）

---

### E7 · 极端流量稳定性

**自变量**：突发倍数（瞬间请求数 / 系统稳态处理能力）

| 倍数 | 请求数 | 观察 |
|---|---|---|
| 1× | 100k | 基线 |
| 5× | 500k | 队列堆积、延迟劣化 |
| 20× | 2M | 拒绝策略生效、是否 OOM |
| 100× | 10M | 崩溃点在哪，如何优雅降级 |

**关注**：堆内存曲线（`-XX:+PrintGCDetails` 或 JFR）、队列峰值深度、拒绝率、是否出现 OOM

## 四、要采集的指标

每次运行都落一行 CSV，字段如下：

```
run_id, experiment, config_name, queue_type, lock_type, workers, vusers,
queue_capacity, rate_limit, dedup_type, persist_enabled,
total_requests, success, failed_soldout, failed_rejected, failed_dup,
tps, p50_ms, p95_ms, p99_ms, p999_ms, max_ms, mean_ms,
queue_peak_depth, gc_count, gc_time_ms, heap_used_peak_mb,
oversold, duplicate_orders, consistency_ok, duration_ms
```

`oversold` 和 `duplicate_orders` 在**每次**运行后都断言，一次不为 0 就整轮作废并记录（这本身也是数据）。

## 六、时间预算（这是需要你拍板的地方）

按上面的完整矩阵，配置组数合计：

| 实验 | 配置组 | 轮次/组 | 总运行次数 | 预估耗时 |
|---|---|---|---|---|
| E1 队列 | 12 | 8 | 96 | ~25 min |
| E2 锁 | 25 | 8 | 200 | ~30 min |
| E3 线程池 | 24 | 5 | 120 | ~20 min |
| E4 限流 | 15 | 5 | 75 | ~15 min |
| E5 去重 | 12 | 5 | 60 | ~10 min |
| E6 恢复 | 4 场景 | 3 | 12 | ~10 min |
| E7 稳定性 | 4 | 3 | 12 | ~40 min（含 100× 要跑很久） |
| **合计** | **92** | | **575** | **~2.5 小时机器时间** |

加上开发时间，我的估计是：
- **引擎 + 实验框架**：2～3 天
- **跑实验 + 出图**：半天（可挂机）
- **面板**：1 天
- **报告**：1～2 天

如果时间紧，**建议砍掉的顺序**是：E7（100× 那档）→ E4 的 R5 自适应 → E3 的 24 组砍一半 → E5 的 Cuckoo 只做代码不做实验。
