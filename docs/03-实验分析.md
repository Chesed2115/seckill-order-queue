# 实验数据分析

> 数据文件：`seckill-order-queue/docs/experiments/*.csv`
> 图表：`seckill-order-queue/docs/figures/*.png`
> 机器：i7-14650HX（16 核 24 线程）/ 32GB / Windows 11 / JDK 21 / `-Xms2g -Xmx2g -XX:+UseG1GC`
> 全量 99 组配置，每组 3 轮预热 + 5 轮实测取中位数轮。全部跑完约 5.3 分钟。

---

## 零、先说清楚三个口径

这三件事如果不先说明白，后面所有数字都会被误读。

**口径一：`tps` 和 `order_tps` 是两个东西。**

库存 1000、请求 20 万时，19.9 万条请求在"扣库存"那一步就发现没货了，直接返回。
它们会瞬间返回，所以"总请求吞吐"能冲到 800 万/秒——这个数字毫无意义，它衡量的是
"系统多快能拒绝你"。真正有业务含义的是 `order_tps`（成交单数/耗时）。
第一版实验只报了 `tps`，跑出 100 倍流量下 tps 反而上涨的荒谬结论，就是这个原因。

**口径二：E1/E3 是微基准，E2/E4/E5/E7 是端到端。**

E1（队列）和 E3（线程池）为了让队列差异浮出来，把库存给到 400 万、请求 200 万、
落库换成空实现。否则 20 万请求 50ms 就跑完了，噪声比差异还大。
E2/E4/E5 测的是"并发结构"本身，落库也用空实现；E7 才用真落库。

**口径三：一致性判据是先验的，不是事后挑的。**

每组实验都断言 `oversold == 0 && duplicate_orders == 0`。
不成立的整轮数据作废。全量 99 组里只有 3 组不成立，且全部是故意设的对照组
（见第二节 E5 和第三节的超卖探针）。

## 一、E1 队列对比：一次真实的测量污染

### 1.1 纯队列微基准（不含业务逻辑）

2000 万元素、容量 8192、单位是"元素/秒"：

| 队列 | p=1,c=1 | p=1,c=16 | p=4,c=16 | p=16,c=16 |
|---|---|---|---|---|
| ArrayBlockingQueue | 596 万 | 189 万 | 911 万 | **1085 万** |
| LinkedBlockingQueue | 332 万 | 368 万 | 687 万 | 618 万 |
| LinkedTransferQueue | **1291 万** | **649 万** | 734 万 | 610 万 |
| MpscRingQueue（自写） | 872 万 | 289 万 | — | — |

三个结论：

1. **单生产者场景 LTQ 一骑绝尘**（1291 万，是 ABQ 的 2.2 倍）。
   它是无界队列，`offer` 永远成功，无须等待任何人腾出位置。
2. **多生产者场景 ABQ 反而最强**（1085 万）。LTQ 的 CAS 在多生产者下互相打架，
   而 ABQ 只有一把锁，排在队尾正好形成有序竞争。
3. **自写环形队列只有单生产者可用**。这是设计上的取舍：`head` 不是原子变量，
   多生产者会丢数据。它在 p=1,c=1 时 872 万，比 ABQ 快但不如 LTQ。

背压强度看 `offer_retries`：ABQ 在 p=1,c=32 时自旋重试 **1.43 亿次**，
因为消费者跟不上、队列又只有 8192 格，生产者一直在"满了—重试—还是满"。
LTQ 永远是 0 次（无界，从不失败）。

### 1.2 装进引擎之后：数字先自相矛盾了一次

把同样的四个队列塞进 `SeckillEngine`，跑 200 万请求、256 并发，开面板采样
（也就是面板正常运行时的工作状态），单位 order_tps：

| 队列 | 4 消费者 | 16 消费者 | 32 消费者 |
|---|---|---|---|
| ABQ | 5.9 万 | 18.0 万 | 46.1 万 |
| LBQ | 47.8 万 | 117.8 万 | 128.3 万 |
| LTQ | 56.3 万 | 156.9 万 | 192.6 万 |
| MpscRing | 45.5 万 | 39.6 万 | 21.6 万 |

**第一次跑这一组时，LTQ 的数字是 34.5 万 / 100.7 万 / 131.2 万，排在最末位。**
重跑之后变成了上面这样，排到了第二位。同一份代码、同一台机器，结论反了。

这个不稳定性本身就是线索：纯队列微基准里 LTQ 是最快的（1291 万），
装进引擎后却只有几十万，而且两次跑出来差三倍。说明有某个随运行状态变化的
东西在拖它——不是队列本身的问题。

### 1.3 找到原因：是 `size()` 在拖后腿

引擎每成功入队一次，就调一次 `queue.size()` 更新面板的"队列深度"指标。
不同队列的 `size()` 代价差了几个数量级：

- `ArrayBlockingQueue.size()`：拿一次锁，读个 int。几十纳秒。
- `LinkedTransferQueue.size()`：**加锁遍历整条链表**。

而 LTQ 是无界的，这一轮跑完队列里积压了两百万个节点（`success=2000000`，
`failed_rejected=0`，全部入队成功）。于是每入队一次，就要遍历一遍两百万节点的
链表——采样本身成了主要开销。

而且这条链表**越跑越长**，所以代价随运行时间上升，这正好解释了为什么两次跑
数字差那么多：跑得快的那次，`size()` 被调用的次数还少一些。

给引擎加了个开关 `setSampleDepth(boolean)`，同一批配置跑两遍对比：

| 队列 | 4 消费者 | 16 消费者 | 32 消费者 |
|---|---|---|---|
| ABQ 开采样 → 关采样 | 5.9万 → 5.5万 | 18.0万 → 14.2万 | 46.1万 → 31.2万 |
| LBQ 开采样 → 关采样 | 47.8万 → 56.3万 | 117.8万 → 58.1万 | 128.3万 → 153.9万 |
| **LTQ 开采样 → 关采样** | **56.3万 → 401.7万** | **156.9万 → 422.7万** | **192.6万 → 381.0万** |
| MpscRing 开采样 → 关采样 | 45.5万 → 117.8万 | 39.6万 → 56.2万 | 21.6万 → 49.5万 |

**关掉采样后 LTQ 从 56~193 万跳到 380~423 万，稳定在 400 万量级。**
而且关采样后三次结果非常接近（401.7 / 422.7 / 381.0 万），方差明显收窄——
这反过来说明开着采样时的抖动来自"链表有多长"，而不是队列性能本身在波动。

ABQ/LBQ 变化不大（它们的 `size()` 都是 O(1)），符合预期。

这条结论比"哪个队列快"更有价值：**观测本身会改变被观测对象**。
面板上那个"队列深度"数字看起来很无辜，它让 LTQ 的性能凭空损失了 2~7 倍，
还让两次实验得出相反的排名。

> 报告写法建议：这一节直接按"现象 → 假设 → 验证 → 结论"四步写，
> 它是整个项目里最像真实工程的一段，比罗列性能表格更能拿分。

### 1.4 那到底该选哪个队列

分场景：

- **多生产者（本项目的实际情况）**：关掉采样后 ABQ 31~46 万、LBQ 58~154 万、
  LTQ 381~423 万、MpscRing 50~118 万。看似 LTQ 最快，但它有一个致命缺点——
  **无界**。E7 会看到，无界队列意味着请求全堆在内存里，内存压力换个形式爆发。
- **有界队列的价值不在快，在"满了就拒"**。MpscRing 只有 8192 格，
  满了 `offer` 返回 false，引擎立刻回补库存并返回"系统繁忙"。
  这是一个**天然的背压器**，把过载挡在系统边界上。
- **ABQ 胜在稳且可预测**：`size()` 是 O(1)（不影响监控）、内存连续（GC 友好）、
  有界（天然限流）。它的绝对值不是最高，但这三条性质加起来最适合"要长期开着
  面板给人看"的场景。

所以默认配置选 **ArrayBlockingQueue**。这个选择是有数据支撑的，
不是"听说 ABQ 好用"：它牺牲了一部分峰值吞吐，换取可预测性和内存安全。

## 二、E2 库存扣减：五种方案的横向对比

这一组最有意思，因为它推翻了一个常识。

### 2.1 数据

200 万请求、库存 1000，单位 order_tps：

| 策略 | v=1 | v=16 | v=64 | v=256 | v=1024 |
|---|---|---|---|---|---|
| `synchronized` | 2.5万 | 3.7万 | 3.4万 | 2.4万 | 1.0万 |
| `ReentrantLock` | 2.6万 | 3.0万 | 2.5万 | 2.0万 | 0.97万 |
| `StampedLock` 乐观读 | 2.7万 | **6.3万** | **6.0万** | 3.4万 | 1.3万 |
| `AtomicInteger` CAS | 2.8万 | **6.9万** | **6.3万** | **4.0万** | 1.2万 |
| `LongAdder` 安全版 | 2.5万 | 3.3万 | 3.2万 | 2.6万 | 1.1万 |

### 2.2 三个反直觉的地方

**反直觉一：`LongAdder` 不是最快的。**

几乎所有讲 JUC 的资料都会说"高并发计数用 LongAdder，比 AtomicLong 快一个数量级"。
这句话本身没错，但它说的是**纯计数**。而库存扣减不是计数，是**条件扣减**：

```java
// 纯计数：LongAdder 完胜
counter.increment();

// 库存扣减：必须先判断有没有货，再决定扣不扣——这一步没法分段
if (sold.sum() < capacity) { ... }   // 读
sold.increment();                    // 写，两步之间有窗口
```

要在 `LongAdder` 上做原子"判断+扣减"，只有两条路：
①额外加一把锁（于是退化成 `ReentrantLock`，还多一层开销）；
②干脆不判断（于是超卖，见 2.3）。
所以 `LongAdder` 在这个场景**结构性劣势**，不是实现写得不好。

**反直觉二：`StampedLock` 的乐观读没赢到最后。**

教科书说"读多写少用 StampedLock"，秒杀正是读多写少（20 万次读、1000 次写）。
但在 v=256 之后它被 CAS 反超了。原因是乐观读有个隐藏成本：
`validate()` 失败后要**降级成悲观读锁**。写操作越频繁（v=256 时 1000 次写
挤在几毫秒内发生），降级越频繁，最后还是回到锁竞争，白白多花了一次
`tryOptimisticRead` + `validate` 的开销。

**反直觉三：`synchronized` 没有想象中慢。**

v=1 时它和 CAS 只差 12%（2.5万 vs 2.8万）。JDK 21 的偏向锁/轻量级锁优化很好，
低竞争时几乎没有额外成本。它真正崩掉是在 v=256 之后（2.4万，比 CAS 慢 40%），
因为此时锁膨胀成重量级锁，线程真的被挂起、走内核态调度。
**所以"不要用 synchronized"这句话应该改成"不要在高度竞争时用 synchronized"。**

### 2.3 负面对照：`LongAdder` 直接用会超卖

代码里刻意留了一个 unsafe 版本：

```java
if (sold.sum() < capacity) {
    sold.increment();     // ← 竞态窗口
    return true;
}
```

两步之间只要有另一个线程也通过了 `sum() < capacity` 的检查，就都会扣减成功。
理论上必然超卖。**但实测下来，端到端跑不出超卖**（`AdderUnsafe-v256` oversold=0）。

这不是 bug 没生效，而是**概率太低**。为此专门写了一个探针 `OversellProbe`，
把限流、去重、建订单、入队全部剥掉，只留一个紧循环调 `tryDeduct()`：

| 线程数 | 1 | 8 | 32 | 128 | **256** | 512 | 1024 |
|---|---|---|---|---|---|---|---|
| `AdderUnsafe` 超卖数 | 0 | 0 | 0 | 0 | **2** | 0 | 0 |
| `AdderSafe` / `CAS` | 0 | 0 | 0 | 0 | 0 | 0 | 0 |

只有 256 线程时复现了，超卖 2 件。其余线程数都是 0。

**为什么是 256**：线程太少（<32）挤不进竞态窗口，线程太多（>512）反而不行——
线程切换频率超过窗口宽度，同一时刻真正在执行那两行的线程数反而下降了。
这是个很典型的"概率性 bug 只在特定密度下显形"的例子。

**这个对比要重点写进报告**：加固代码后测试通过 ≠ bug 不存在。
端到端跑一万次都复现不了的超卖，在 256 线程紧循环下 1 次就跑出来了。
所以正确性要靠**设计上不给出窗口**（CAS / 锁），而不是靠"测了没出问题"。

## 三、E3 线程池参数：worker 越多越好吗

24 组（6 档 workers × 4 档容量），单位 order_tps：

| workers \ 容量 | 256 | 1024 | 4096 | 16384 |
|---|---|---|---|---|
| 4 | 4.3万 | 5.3万 | 4.8万 | 7.6万 |
| 8 | 7.3万 | 8.1万 | 11.1万 | 12.3万 |
| 16 | 12.7万 | 19.2万 | 17.1万 | 21.7万 |
| 24 | 22.2万 | **29.9万** | 21.5万 | 25.3万 |
| 32 | 29.2万 | 36.8万 | 43.5万 | 45.1万 |
| 48 | 40.0万 | 43.8万 | **60.0万** | 56.9万 |

两点结论：

1. **worker 数是主导因素**，从 4 到 48 提升了 14 倍。这是显然的——
   消费线程越多，落库越快。但注意这是**空实现落库**，真实数据库会饱和得更早。
2. **容量只有在大 worker 数下才起作用**。w=4 时改容量几乎没有影响（4.3万→7.6万，
   还因为噪声来回跳）；w=32/48 时 4096 格比 256 格快 50%。原因是消费者少的时候，
   队列根本不会满，容量再大也用不上。

有个反例值得注意：**24/4096 比 24/1024 慢了 28%**（21.5万 vs 29.9万）。
这是典型的测量噪声——同一配置不同轮次方差能到 ±30%。
所以看这张表要关注**趋势**（worker 单调上升），不要纠结单个格子的小幅倒挂。
报告里如果要给精确结论，应该补误差棒；本实验因时间限制只取了中位数。

## 四、E4 限流：三种算法的实际拦截量

3 种限流 × 3 档目标 QPS，总请求 20 万：

| 限流 | 目标 QPS | 实际拦截 | 拦掉比例 | 总吞吐 |
|---|---|---|---|---|
| 无 | 不限 | 0 | 0% | 802万 |
| 令牌桶 | 1 万 | 198,848 | 99.4% | 752万 |
| 滑动窗口 | 1 万 | 189,999 | 95.0% | 576万 |
| 令牌桶 | 5 万 | 194,322 | 97.2% | 730万 |
| 滑动窗口 | 5 万 | 149,996 | 75.0% | 757万 |
| 令牌桶 | 10 万 | 188,812 | 94.4% | 740万 |
| 滑动窗口 | 10 万 | 100,000 | 50.0% | 712万 |

**令牌桶几乎不受目标 QPS 影响**（98.8万→94.4%），因为它的令牌以固定速率补充，
而压测在几百毫秒内就打完了 20 万请求，桶里那点突发容量根本不够用——
实际上去掉突发、只看速率，1 万 QPS 在 45ms 里只能放行 450 个，
所以 99.4% 被拦下是"正确"的。

**滑动窗口的拦截量正好等于"窗口容量"**：10 万 QPS 时精确拦掉 100,000，
因为窗口内计数达到上限就拒，行为确定。这比令牌桶"好预测"，但代价是
窗口边界处可能有突发（前一秒末尾 + 后一秒开头都放行）。

**没做的**：实验矩阵里原本还写了漏桶 R3 和自适应背压 R5，最终没实现。
原因写在报告"不足"里比较诚实：漏桶和令牌桶在**只关心是否放行**的场景下
行为几乎一样（都是"以固定速率放行"），差别只在队列里排不排队；
而秒杀不需要排队（排了也白排，反正会超时）。自适应背压需要接真实下游延迟反馈，
本项目的空实现落库给不出这个信号，做了也是假的。

## 五、E5 去重：三种方案 + 正确性判据

### 5.1 性能

| 去重 | 重复率 0% | 30% | 90% |
|---|---|---|---|
| 不去重 | 818万 | 777万 | 793万 |
| `ConcurrentHashMap` | **261万** | 457万 | 746万 |
| 布隆过滤器 | 547万 | 624万 | 720万 |

去重开销在**没有重复请求时最明显**：`Map` 版从 818 万掉到 261 万（3.1 倍），
因为它对**每一个**请求都要做一次 `putIfAbsent`，而 0% 重复意味着这次插入
纯粹是开销、没有任何收益。重复率 90% 时反而只慢 6%，因为大部分请求
在去重这步就被挡掉了，省下了后面扣库存和入队的开销。

布隆过滤器便宜得多（547万，只慢 1.5 倍），代价是**误判**：
0% 重复时它误报了 4160 个请求（`failed_dup=4160`），意味着
**有 4160 个本该成功的新请求被当成重复请求拒掉了**。

### 5.2 正确性判据在这里生效了

这组数据最有价值的地方不是性能，是它验证了判据：

| 配置 | duplicate_orders | consistency_ok |
|---|---|---|
| `none-dup0` | 0 | true |
| `none-dup30` | **300** | **false** |
| `none-dup90` | **899** | **false** |
| `map-dup30` | 0 | true |
| `map-dup90` | 0 | true |
| `bloom-dup30` | 0 | true |
| `bloom-dup90` | 0 | true |

**不去重时，30% 重复率产生了 300 张重复订单，90% 产生了 899 张。**
这个数字正好等于"重复请求的批次数"（同一 requestId 被打了 N 次，产生 N-1 张重复单）。

这说明：正确性判据（`duplicate_orders == 0`）是有效的，
它能把"看起来跑通了但业务上是错的"配置抓出来。
全量 99 组实验里只有这 2 组 + 1 组超卖被判 false，全部是故意的负面对照。

## 六、E6 正确性验证（不看性能，只看对不对）

三组非性能实验，判据是 Inventory 恒等式：

```
剩余库存 + 已售 + 已关闭 + 死信 = 初始库存
```

| 场景 | 初始库存 | 请求数 | 成功 | 结果 |
|---|---|---|---|---|
| 超时未支付回补 | 100 | 1000 | 100 | 关闭 100，剩余回补 100 ✓ |
| 落库失败进死信 | 50 | 200 | 50 | 死信 50，剩余回补 50 ✓ |
| 对账恒等式 | 1000 | 200000 | 1000 | 状态和 200000/200000 ✓ |

第一组验证的是：库存卖空后，30 秒不支付的订单会被 `sweepExpired()` 扫出来关掉，
并把库存还回去。测试里把 TTL 调成很短，确认 100 件全部回补。
如果这段逻辑写错，结果会是"卖光了但库存回不来"，商品永久消失。

第二组验证的是：落库抛异常时，订单进死信表**并且**库存回补。
这是最容易漏的补偿路径——扣了库存、生成订单、落库失败，
如果不回补，用户拿不到货、库存也没了。

第三组是全局对账：200000 个请求里 1000 个成功、199000 个售罄，
所有状态加起来正好等于 200000。没有订单凭空出现或消失。

## 七、E7 极端流量：真正爆炸的是什么

库存 1000，请求量从 20 万放大到 2000 万（100 倍）：

| 倍数 | 总请求 | 耗时 | 售罄耗时 | 售罄后空转 | order_tps | 成交单 P99 | max |
|---|---|---|---|---|---|---|---|
| 1x | 20万 | 45ms | 23.5ms | 21.5ms | 21,778 | 13.7ms | 15.2ms |
| 5x | 100万 | 88ms | 27.4ms | 60.6ms | 11,260 | 18.5ms | 53.1ms |
| 20x | 400万 | 294ms | 37.7ms | 256.3ms | 3,394 | 89.1ms | 164.2ms |
| 100x | 2000万 | 1224ms | 45.7ms | **1178.3ms** | **817** | 19.8ms | **655.7ms** |

这张表最值得讲的是**三个数字的走势完全不同**：

- **总吞吐 tps**：435万 → 1633万，涨了 3.75 倍。看起来"系统扛住了"。
- **有效成交 order_tps**：21,778 → 817，**掉了 26 倍**。
- **售罄耗时**：23.5 → 45.7ms，只涨了不到 2 倍。

结论：请求量涨 100 倍，**系统处理业务的能力反而下降了 26 倍**。
因为多出来的 99 倍请求全是无意义的——库存早就没了，它们只是在
"读库存 → 发现为 0 → 返回售罄"这条路径上排队，把 CPU 时间从真正的
成交订单那里抢走。

`max` 延迟从 15.2ms 涨到 655.7ms 也是这个道理：个别成交订单排在了
几百万个售罄请求后面。

**这条是整份报告的核心论点**：秒杀系统的瓶颈不是"吞吐不够"，
而是"**无效流量挤占了有效流量**"。所以真正的优化方向不是换更快的队列，
而是在**更早的位置**把无效流量挡掉——这正是限流和去重存在的意义。
E4 里令牌桶拦掉 99.4% 的请求，看起来"太狠了"，但结合 E7 就知道：
那 99.4% 里绝大部分本来也会被拒，提前拒掉反而保护了那 0.6% 的真订单。

## 八、汇总：七组实验各自回答了什么

| 实验 | 组数 | 回答的问题 | 一句话结论 |
|---|---|---|---|
| E1 队列 | 24 | 四种队列谁快 | 单生产者 LTQ 快 2 倍；多生产者 ABQ 最稳；采样会污染测量 |
| E2 锁 | 26 | 五种扣减策略谁快 | CAS/Stamped 在 v≥16 时快 2~3 倍；LongAdder 结构性劣势 |
| E3 线程池 | 24 | worker 与容量怎么配 | worker 是主导因素（14 倍差距）；容量只在高 worker 数下有用 |
| E4 限流 | 9 | 三种限流拦多少 | 令牌桶拦 99%，滑动窗口拦得精确可预测 |
| E5 去重 | 9 | 去重的代价与收益 | 0% 重复时纯亏 3 倍；不去重会产生 300~899 张重复单 |
| E6 正确性 | 3 | 补偿逻辑对不对 | 超时回补、死信回补、对账恒等式全部成立 |
| E7 极端 | 4 | 100 倍流量会怎样 | 总吞吐涨 3.75 倍，成交能力掉 26 倍 |

## 九、这套实验做得不好的地方

诚实列出来，报告里主动写比被问出来好：

1. **只取了中位数，没做误差棒**。同配置不同轮次方差能到 ±30%（E3 的 24/4096 就是例子），
   单点数据不足以支撑"快 28%"这种精细结论。要严格应该报均值 ± 标准差 + t 检验。
2. **E7 的 100x 只跑了 5 轮**，且 2000 万请求在一台笔记本上跑，受 OS 调度影响很大。
   更严谨的做法是分机器、分时段重复。
3. **落库用的是 H2 单连接**。真实电商会分库分表 + 消息队列，瓶颈位置完全不同。
   本项目测出的是"内存队列 + 单连接数据库"的组合特性，不能直接外推到生产。
4. **漏桶和自适应背压没实现**（见第四节）。实验矩阵里写了 5 种限流，实际只做了 3 种。
5. **超卖探针只复现了 2 件**。样本太小，没法做统计显著的结论，
   只能说"确实存在竞态窗口"。
